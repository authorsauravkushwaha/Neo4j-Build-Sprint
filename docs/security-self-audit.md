## Coverage

### In scope

- Authentication and authorisation on every handler this repository ships, including cross-user access attempts.
- Input handling: malformed JSON, oversized bodies, injection-shaped strings, prototype-pollution keys, unknown fields.
- Rate limiting and request-signing behaviour, driven through the real handler stack.
- Response hygiene: error codes without internals, security headers, cache directives, and whether any credential-shaped value reaches a response.
- The workflow engine as an attack surface: the reference grammar, the URL allow-list, and the run log.
- The second storage backend, where the ownership policy lives in code rather than in the database, and where the declared collections must match the tables the store actually uses.

### Out of scope, and why

- **Anything reachable only over the network** — The checks call the handlers in-process. There is no --target flag, by design: this is a self-audit, not a scanner.
- **The database itself** — Row-level security is verified separately by `npm run verify:rls` against a real Postgres, which is the only place it can be verified.
- **The browser** — CSP behaviour, third-party script execution and clickjacking need a real browser: `npm run verify:browser`.
- **Dependency vulnerabilities** — That is `npm audit` and Dependabot’s job; a rules-based harness would only duplicate it worse.
- **Timing side channels and statistical attacks** — They need many samples and a stable host; a small probe would produce noise, not a finding.
- **The hosted Supabase platform** — Auth, storage and the Postgres instance are somebody else’s audited surface. What is ours is the code above them.
